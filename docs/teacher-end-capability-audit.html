功能审查报告 · v3 · Teacher-Side Capability Audit

教师端功能审查：功能不少，但「教师」缺席

v2 报告给出的判断是「闭环已通，特色未立」。本轮按代码逐项复核后，结论要更精确一些：教师端的模块数量并不少——14 个路由、12 张教师专属业务表、22 个 AI 工具、7 枚教师徽章，横向对比开源校园系统已属中上。真正的问题不在「量」，而在两处结构性错位：一是所有能力都以「学生」为坐标，教师是操作员而不是主角；二是所有能力都盘踞在「育人事务」一条线上，主流教师端赖以成立的「教学」那条线整体缺位。

审查范围：14 个路由 · 12 张业务表 · 9 个服务 · 22 个 AI 工具 对标：教务类 / 互动教学类 / 协同管理类 三条产品线 结论：能力不缺，坐标错了 18 项补强 · 4 个阶段

核心结论

不是「功能太少」，是「功能的坐标系装错了」——所有能力都以学生为主体、以育人为轴线，教师既没有自己在产品里的位置，也没有属于教师行业的主业。

把教师端的能力摊开数：统一待办 TeacherTask、危机四级闭环、关怀中心三子域、家校沟通留痕、公告真实触达回执、匿名互评、教师 e-Portfolio、AI 主动洞察 + 周报、22 个可被对话调用的工具——单看清单，这已经比多数开源校园系统厚重。所以「感觉太少」不是数量错觉，而是打开之后找不到「我」和「我的课」带来的空洞感。

两处错位是根因：其一，缺「我」——教师的一切数据都是「我的学生怎样」，没有「我做得怎样、我成长到哪、我的付出值多少」。侧栏「我的工作台」分组只有 1 项，是最直白的证据。其二，缺「课」——Course 表里教师是 String(50) 而非外键，TeacherSchedule 是私人备忘而非课表，考勤 / 作业 / 成绩录入 / 听课评课一条都没有。教师端只有「辅导员」的一半，没有「教师」的另一半。

已经很强 · 别推翻

育人事务的闭环密度

危机四级状态机、待办统一表与幂等去重、公告真实已读回执、匿名互评的 HMAC 匿名令牌——这几处工程完成度高于同类产品，是护城河。

结构性缺口 · 教师缺席

没有一页属于教师自己

教师徽章 7 枚、e-Portfolio 四段式、成长值等级——素材全齐，但没有承载页。能力被埋在学生档案页和社交化资料卡里。

结构性缺口 · 教学缺位

没有课表、没有课堂

主流教师端的第一屏是「今天上什么课、哪个班、几个人没到」。这一整条线在本项目里是空的。

2三个结构性病灶

把上面的盘点往下挖一层，会看到三处「表结构 / 数据模型」层面的错位。它们的共同特征：不是缺模块，而是既有数据用错了方式建模，导致再怎么加功能也长不出教师的视角。

2.1 病灶一：Course.teacher 是字符串，不是外键

backend/app/models/academic.py:62 里，课程的授课教师字段是 teacher: Mapped[str] = mapped_column(String(50))。这意味着：

  • 系统无法回答「张老师教哪些课」——只能靠姓名模糊匹配，同名即错
  • 教师端无法按「我的课」过滤任何数据：全站教师数据范围一律是 User.tutor_id == user.id（见 api/academic.py、api/crisis.py、api/announcement.py、api/care_center.py、api/care_record.py 共 20 余处）
  • 「我教的班」与「我带的班」在数据层是同一个东西，进一步强化了「教师 = 辅导员」的单一定位
这是本轮审查发现的最关键一行代码。只要 Course.teacher 不落成 teacher_id，第五章要说的课表、考勤、作业、成绩、课堂表现——全部无法落地。它是整条教学线的总闸。改造代价极低（新增列 + 数据回填 + 保留字符串做兼容），收益是解锁整个「教学」域。

2.2 病灶二：TeacherSchedule 是私人备忘，不是课表

models/announcement.py:38 的 TeacherSchedule 只有 date / content / urgency / completed 五个业务字段——它是教师手记的日程条目，不是排课数据。教师端首页的「桌面日程」（HomeDesktopSchedule.vue）渲染的就是它。

而真正结构化的课表在 Course 表里（day_of_week / start_period / end_period / week_start / week_end / location），却被学生端 SchedulePage.vue 独占使用，「第 N 教学周」这个概念也只在学生端出现。教师端看不到自己的课表视图。这解释了为什么教师端首页「看起来像 HR 系统而不像教师应用」——真正的教师应用第一屏是课表。

2.3 病灶三：DashboardOut 只有 5 个数字，且没有一个是「我」的

api/teacher.py:88 的 dashboard_stats 返回字段只有：

字段含义主语
total_students名下学生总数学生
alert_countAI 对话预警总数学生
pending_leave_count待批请假数学生
severe_alert_count高危预警数学生
resolved_alert_count已闭环预警数学生

5 个指标全部以学生为主语，没有「今日待办 / 本周家访 / 待回访家长 / 我的响应时长 / 我的关怀密度」中的任何一个。而讽刺的是，这些数据后端全都已经存在：TeacherTask 有待办状态、HomeVisitRecord 有回访状态、GuardianContactLog 有留痕、CareRecord 有记录——只是没有一个接口把它们聚合成「我的履职」。这是典型的数据齐、视角缺。

2.4 三个病灶的共同根因

Root Cause

产品把「教师」定义成了「学生数据的管理者」，而不是「一个有职业成长与教学主业的专业角色」。

这一定义贯穿了数据模型（教师没有课程外键）、接口设计（教师数据范围 = 名下学生）、信息架构（「我的工作台」只有一项）、界面语言（KPI 全说学生）。用户感受到的「太少」「没特色」，是这一定义在体验层的必然结果。

要改的不是「加功能」，而是换主语：把教师从「第三人称的操作者」改为「第一人称的主体」。第四章给出的方案，本质上是这件事的界面与数据落地。

3主流教师端对标矩阵

市面上的教师端大致分三条产品线，各自的「杀手级界面」完全不同。本项目只覆盖了第三条线的一部分，这是「没有市面上主流教师端特色」的直接原因。

教务线

正方 / 金智 / 强智

杀手界面：课表 + 点名 + 成绩录入。用户预期：打开就是「今天第 3-4 节，计科 2201，应到 42 实到 39」。本项目覆盖度：约 1 成。

互动教学线

学习通 / 雨课堂 / 智慧职教

杀手界面：课堂活动流（签到、抢答、随堂测、作业、讨论）。用户预期：课上手机就是遥控器。本项目覆盖度：0。

协同育人线

钉钉教育版 / 企业微信 / 今日校园

杀手界面：待办 + 通知 + 审批 + 沟通。用户预期：一件事从头到尾有人管。本项目覆盖度：约 7 成，是唯一有护城河的一条。

4个人特色：把「教师」放回第一人称

这一章解决「没有教师端个人特色」。核心判断是：素材已经齐了，缺的是承载页与叙事。不需要新造业务，只需要把已经躺在数据库里的东西，换一个主语重新呈现。

  • 走进家门 🏠 3 次家访
  • 及时表扬 🌻 5 次正向激励

6 级等级阶梯 + 成长值

新芽 0 → 幼苗 60 → 青苗 180 → 繁花 400 → 硕果 800 → 领航 1500

⚠ 问题：这套等级与学生端共用，文案是 C 端游戏化语言（「刚刚开启校园智能之旅」）。对一个 35 岁的辅导员说「你是新芽」，不会产生职业认同，只会产生违和感。教师激励必须换语言。

4.2 建议一：新增「我的育人成长」独立页面（My Growth）

这是本轮最重要的一个建议。它的位置不是「再加一个功能」，而是把散落的教师侧数据第一次聚合成一个叙事完整的页面。建议路由 /teacher/me，并置于侧栏「我的工作台」分组首位。

A
履职画像 —— 「我做了什么」

四维指标 + 环比：关怀密度（CareRecord）、家访完成（HomeVisitRecord + 回访状态）、家校留痕（GuardianContactLog）、待办办结率（TeacherTask done/total）。数据全部已存在，只需一个 /api/teacher/me/profile 聚合接口。这是最能让教师产生「被看见」感的一屏。

B
成长轨迹 —— 「我走到哪了」

把 TeacherPortfolioItem（工作案例 / 荣誉 / 培训研修 / 工作研究成果）+ 徽章解锁 + 等级晋升合并成一条时间线；配一张育人影响力曲线（覆盖学生数 × 关怀次数 × 闭环率）。

C
专业能力雷达 —— 「我强在哪、弱在哪」

对标《高等学校辅导员职业能力标准（暂行）》九项能力：思想理论教育、党团建设、学业指导、心理健康、网络思政、危机应对、职业规划、资助育人、班级管理。初始分由既有业务自动折算，后续可由 PeerSurvey 的「我的被评」聚合分回填（reviewer_id / review_comment 字段就是为此预留的）。

为什么这一页能立住「教师端个人特色」：调研的 20+ 个开源校园系统没有一个有独立的教师成长模块——它们都有教师端，但教师端里没有「教师」。这一页做出来，就是产品层面唯一的、抄不走的差异点。它同时也是把「育人事务」升华为「教师职业发展」的枢纽：每一件琐事都会在这里变成一次成长。

5主流特色：补上「教学」这条线

这一章解决「没有市面上主流教师端特色」。策略上不建议真去对标学习通做全套互动教学——那是另一个产品。建议只补主流教师端「不可或缺的最小集」，并且用本项目已有的 AI 与闭环优势去做差异化。

5.1 前置改造：一条几乎零成本、解锁全局的迁移

把 Course.teacher: str 改为 teacher_id: int | FK

  • 迁移方案：新增 teacher_id 列（可空）→ 回填脚本按 Course.teacher 字符串匹配 User.name + role=teacher → 无法唯一匹配的记录留空并输出核对清单 → 保留原字符串列一学期做兼容读兜底 → 教师端接口增加 OR (teacher_id = me) OR (teacher_id IS NULL AND teacher = my_name) 过渡查询
  • 影响面：仅 models/academic.py、api/academic.py 两处；现有学生端课程查询走 class_group_id，完全不受影响
  • 收益：解锁「我的课表 / 我的课堂 / 我的成绩录入 / 我的作业」全部四个模块；让「我教的班」与「我带的班」第一次在数据上分开

5.2 四个必修模块

① 我的课表与教学周

为什么必须有：主流教师端的第一屏。打开就知道「今天几节课、在哪、哪个班、第几教学周」。

做什么：复用学生端 SchedulePage.vue 的周课表组件（已相当成熟），改为按 Course.teacher_id == me 过滤；顶部加「第 N 教学周 + 下次上课倒计时 + 今日课时数」；点击课程卡弹出当次课堂面板（考勤入口）。

成本：低（组件复用 + 一个查询接口）。强烈建议作为教学线第一件事。

② 课堂考勤与请假联动

为什么必须有：点名是教师端使用频率最高的动作，也是「课堂」这个概念的入口。

做什么：新增 Attendance 模型（course_id / date / period / student_id / status: present/absent/late/leave）；一次点名按班批量落库；关键差异化——点名时自动比对当次时间窗内的 LeaveRequest，已批假的自动标为 leave 不误判旷课；未批假缺勤一键生成 TeacherTask（来源 follow_up）通知本人与辅导员。

成本：中。差异化点：主流产品的考勤与请假是两张皮，本项目能天然打通。

③ 成绩录入与学业预警联动

为什么必须有：成绩是教师的「产出」，无录入则教师端永远只是行政工具。

做什么：按课程批量录入（表格粘贴 / Excel 导入）；自动算 GPA 与班级分布；出及格率、优秀率、班级排名趋势（跨学期）；关键差异化——低于阈值自动触发既有 alert_pipeline（新增一条 grade_low 规则），生成学业预警与跟进任务，与「人文关怀 · 学业预警类关怀事件」自动衔接。

成本：中。差异化点：成绩→预警→关怀→跟进，闭环跑通的产品极少。

④ 作业布置与提交跟踪

为什么必须有：是「教学过程」里唯一能留下频次数据的载体，且直接喂给学情画像。

做什么：布置（题目 / 附件 / 截止时间）→ 学生提交 → 教师批改（分数 + 评语）→ 退回重做；关键差异化——提交率与未交名单直接进「履职画像」与「学生画像」，未交学生自动进 AI 洞察的「建议联系」候选，而不是靠教师手工翻。

成本：中高（涉及学生端提交页）。可后置到第 3 阶段。

5.3 两个低成本高观感的补强

⑤
未读催办：把已实现的「触达回执」用满

公告页已有真实 AnnouncementRead 回执与触达率。只差一步：点击触达率数字 → 展开未读学生名单 → 一键「站内提醒 / 生成本人待办 / 通知家长」。这是从「知道有几个人没看」到「让没看的人看到」的闭环最后一击，改动极小，体感极强。

⑥
预警规则可视化：把 alert_pipeline 的能力开放给教师

alert_pipeline_service.py 已支持完整规则结构（code / name / verb / metric / threshold / window_days / baseline_days / due_in_days），且优先读 SystemSetting。但前端没有任何配置入口，默认只有「频繁请假」与「近期学情沉默」两条规则。建议加一个规则管理页（教师可管自己班级的规则、管理员管全校），教师能自定义「连续两周成绩下滑」「连续三次未交作业」「夜间求助 2 次」这类真正贴合自己班级的规则。这是把规则引擎从暗处搬到明处的关键一步。

6被忽略的优势：实时能力已经具备

审查中发现一个容易被低估的事实：本项目已经具备做主流教师端「实时课堂」的底层能力，只是还没接上教学场景。这一点值得单独指出，因为它意味着「互动教学」不需要从零建。

已有能力位置当前用途可迁移到的教学场景
WebSocket 管理器 services/ws_manager.py 消息实时推送、在线状态 点名实时同步（教师端点，学生端立即看到自己被点到）、课堂签到倒计时广播
SSE 流式对话 AgentPage.vue + agent 服务 绵小城对话流式输出 课堂实时问答、AI 现场答疑投影

桌面常驻宠物 DesktopPet.vue + PetChatPanel.vue 陪伴式问答入口 课前 5 分钟主动提醒「下节课计科 2201，上次有 2 人未交作业」——这是主流产品都还没有的「主动副驾」
战略判断：不必去追学习通的「抢答 / 弹幕 / 随堂测」全家桶，那是重投入的军备竞赛且很难超越。更聪明的路线是用已有的 AI 常驻副驾 + 闭环待办，做「事务型教师端里最懂教学的，教学型教师端里最省事的」。点名、成绩、作业三件做到位，加上主动提醒，教师体感已经超过九成产品的日常使用深度。

8结语与取舍建议

一句话回答

功能不少，坐标错了。教师端需要两次视角切换：从「学生的管理者」切到「第一人称的主体」，从「只有育人」切到「育人 + 教学」。

如果是预算有限、只能做三件事，建议按这个顺序：① 重排侧栏 + 上线「我的育人成长」主页（立刻解决「没个人特色」，零新增业务表）→ ② 迁移 Course.teacher_id（解锁教学线）→ ③ 上「我的课表」（立刻解决「不像教师端」）。这三件做完，用户打开教师端的第一感受就会完全不同。

如果预算充足，第五章的考勤与成绩才是真正补齐「主流教师端」的部分。但要清醒一点：不要试图在互动教学上与学习通正面竞争。本项目真正的机会在于——主流产品要么只管教学不管育人，要么只管育人不管教学，而「点完名发现 2 人缺勤，一键就变成跟进任务；批完作业发现 3 人连续低分，自动生成学业预警关怀事件」这个动作，市面上还没有产品能一气呵成地做完。这比多做十个课堂小工具更有价值。

建议优先阅读/决策的三个问题

  1. 教师端的服务对象到底包含不含「任课教师」？如果平台定位永远只是「辅导员工作台」，第五章可以大幅缩减为「课表 + 成绩查看」两项，把重心全押在第四章的个人成长上。这个定位必须先定，否则第 03 项迁移不该启动。
  2. 「我的育人成长」主页由谁看？仅教师本人可见？还是院系领导也能看（即变成考核工具）？这直接决定指标的取舍与隐私边界，也决定 TeacherPortfolioItem.visibility 的默认值是否需要调整。
  3. 教师等级是否与任何实际权益挂钩？若只是荣誉，现有游戏化即可；若要挂钩评优、进修推荐，则等级计算规则必须可审计、可申诉，需要在 PH1 就设计好快照与追溯机制。
一个提醒：本报告指出的最大风险不在功能，而在命名与自我认知。侧栏那个叫「教学工作」的分组里全是学生事务——这种名实不符会持续误导后续开发者的判断（新功能该放哪？会倾向于往「教学」组塞学生功能）。先改名字，比先加功能更重要。
