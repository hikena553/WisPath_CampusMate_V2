实现规划 · v1 · Implementation Plan

教师端改进 · 模块化实现规划

25 项设计已逐项确认。本规划把它们拆成独立数据模型 + 独立 API + 独立服务 + 独立前端组件的模块，明确依赖顺序与验收标准，确保高内聚、低耦合，且每个模块都能单独交付。

定位：高校辅导员工作台 25 项设计 · 4 个阶段 模块化 · 高内聚低耦合 智能体工具同步集成

0架构原则

沿用现有工程的既有约定（models/ + api/ + services/ + registry.py 统一登记），新增能力全部按同一骨架落地，不引入新范式。

分层

四层骨架，单向依赖

API 层只做参数校验与编排，业务规则全部下沉到 Service 层，数据访问只通过 Model 层。禁止 API 里直接写复杂业务逻辑。

边界

一模块一域，不互相 import

跨模块协作只通过 Service 公开函数或事件表，不允许 A 模块的 API 直接调用 B 模块的内部实现。

可插拔

注册即接入，删除即下线

每个模块在 registry.py 追加一行完成接入；模块自身不修改 main.py 或其它模块的代码。

命名约定：模型 models/<domain>.py；接口 api/<domain>.py（prefix=/api/<domain>）；服务 services/<domain>_service.py；前端页面 views/teacher/<Domain>Page.vue，组件 components/teacher/<domain>/。表名统一复数下划线，外键统一 <entity>_id。
强制项 · 智能体工具同步：每个新增模块必须同时在 services/tools/ 下注册对应的智能体工具（definitions.py 登记 + dispatcher.py 分发），确保绵小城智能体可调用，这是项目既有硬约束。

2依赖顺序与关键路径

有依赖关系的模块必须串行，无依赖的可以并行开发。核心判断：任务层是所有闭环的公共基座，必须最先做。

关键路径：统一待办任务层（模块 1）→ 教师侧写记录（模块 2）→ 其它 P0 模块。原因：随访提醒、AI 建议落库、销假待办、关怀计划全部要挂到 TeacherTask 上；工作量统计也要读侧写记录。这两块不先落地，后面的闭环都会退化成"假闭环"。
B
底座层（无依赖，可并行）

学情数据底座（模块 12）· 审批流程引擎（模块 14）。这两块只提供能力，不依赖任何新模块，但被 P0 的部分功能引用——建议与 P0 同期启动，P2 才验收。

C
依赖层（串行）

预警 pipeline（模块 15）依赖 12 + 1；AI 学情助手（模块 13）依赖 12；家校沟通（模块 11）依赖 2 与既有 crisis/leave。

D
独立层（无依赖，可并行）

成长档案（8）· 匿名问卷互评（9）· 关怀中心（10）· 教师工作台（7）。这四个模块互不依赖，是 P1 的主要交付物，可多线并行。

3P0 任务卡（补闭环）

每张任务卡给出：数据模型字段、接口签名、前端改动、验收标准。P0 全部完成即代表"流程能转起来"。

3.1 模块 1 · 统一待办任务层 公共基座

数据模型 TeacherTask

id · teacher_id（负责人）· source_type（枚举：ai_suggest / follow_up / approval / care_plan / alert / manual）· source_id（关联对象 id）· student_id（可空）· title · detail · status（枚举：pending / contacted / cared / done / expired）· due_at · done_at · created_at · updated_at

唯一约束：(source_type, source_id, teacher_id) 唯一，从数据库层杜绝重复推荐（对应设计里"避免重复推荐"）。

接口

GET /api/teacher-tasks（按 status / source_type / due 筛选，分页）· POST /api/teacher-tasks（手动建）· PATCH /api/teacher-tasks/{id}（改状态，状态机校验）· GET /api/teacher-tasks/summary（今日待跟进 / 逾期 / 本周完成数，供首页 KPI）

前端

components/teacher/task/TaskCard.vue（单条卡片，含状态流转按钮）、TaskList.vue（列表 + 筛选）；首页 KPI 卡片增加"今日待跟进"。

验收标准

① 同一 AI 建议重复触发不产生重复任务；② 首页能显示今日待跟进数；③ 任务状态可流转且非法流转被拒。

3.2 模块 2 · 教师侧写记录 工作量数据源

数据模型 CareRecord

id · student_id · teacher_id · record_type（枚举：care 关怀记录 / talk 谈心谈话 / comment 评语）· content · is_private（是否仅教师可见）· task_id（可空，回链任务）· created_at

设计要点：该表同时是"工作量统计"的唯一数据源，成长看板的工作量趋势直接读它，不再另建计数表。

接口

GET /api/care-records?student_id=（按学生聚合）· POST /api/care-records · PATCH /api/care-records/{id} · DELETE /api/care-records/{id}（软删除）

前端

StudentsPage 在现有只读 5 个 Tab 后新增"工作记录"可写 Tab；支持从任务卡"记录关怀"一键带出表单。

验收标准

① 教师可写入三类记录并回显；② 记录可关联任务；③ 删除为软删除、数据可追溯。

4P1 任务卡（补维度）

这四个模块相互独立，是本期的"特色交付物"。全部按独立域实现，彼此不 import。

4.1 模块 7 · 教师个人工作台

形态：不新建页面，重构 HomePage.vue 第二屏，以"我"为主语组织三块内容——今日待办聚合（读 teacher_task summary）、周计划（复用既有日程）、工作量统计（读 care_record + 审批数）。

耦合控制：三块各自封装为独立组件（TodayTasksCard / WeekPlanCard / WorkloadCard），首页只做布局编排，数据由各组件自己拉取。

验收：首页打开即可回答"我今天该做什么"；三块数据与各自源模块一致。

4.2 模块 8 · 教师成长档案（e-Portfolio）

数据模型 TeacherPortfolioItem

id · teacher_id · item_type（枚举：case 工作案例 / honor 荣誉 / training 培训研修 / research 工作研究成果）· title · evidence_json（证据附件 / 链接）· reflection（反思）· occurred_on · visibility（私有 / 公开）· created_at

四段式：证据 → 反思 → 展示 → 评价。评价段留 reviewer_id / review_comment（可空，为后续互评预留）。

接口：GET/POST/PATCH/DELETE /api/teacher-portfolio + GET /api/teacher-portfolio/report（成长报告数据，前端复用打印方案导出）。

前端：PortfolioPage.vue + components/teacher/portfolio/（时间线、条目卡、编辑表单）。

验收：四类条目可增删改；能生成并导出成长报告。

4.3 模块 9 · 匿名工作问卷互评

数据模型

PeerSurvey：id · title · target_type（peer 辅导员互评 / student 学生评辅导员）· period（学期 / 自定义）· questions_json · status（draft / open / closed）· created_by
PeerSurveyResponse：id · survey_id · target_teacher_id · scores_json · suggestion · submitted_at · 无 submitter_id（匿名保证：数据库层不存填写人）

匿名硬约束：答卷表不设提交人字段，从存储层杜绝回溯；接口只返回聚合分布（均分 / 分布 / 匿名建议列表），任何单条答卷不出接口。

接口：POST /api/peer-surveys（建问卷）· POST /api/peer-surveys/{id}/responses（匿名提交）· GET /api/peer-surveys/{id}/result（仅聚合）· GET /api/peer-surveys/mine（我的被评结果）

验收：答卷不可回溯到个人；同一人重复提交有防重（按 问卷+被评人 限一次，用匿名令牌而非身份）；结果页只有聚合数据。

4.4 模块 10 · 人文关怀中心

三个子域，同一模块内聚：

① CareEvent（关怀日历事件：生日 / 困难学生 / 学业预警，event_type + event_date + student_id，支持自动生成与手动添加）
② HomeVisitRecord（家访记录：时间 / 方式 / 对象 / 内容 / 后续计划）
③ PraiseRecord（正向激励：表扬 / 徽章，praise_type + reason）

匿名求助入口：不建新表，复用既有 Feedback 匿名通道（feedback.py），在关怀中心页面提供入口即可，避免重复实现。

验收：日历能自动列出当月关怀事项；家访与表扬可记录；匿名求助可直达既有反馈流。

4.5 模块 11 · 家校沟通（家长观察者）

数据模型（3 张新表，按 A1–A10 定稿）

Guardian：student_id · name · relation · phone · is_primary · remark（无账号、无登录）
GuardianContactLog：student_id · guardian_id · teacher_id · scene（五类场景）· channel（sms / report / link / note）· status（sent / pending / failed / draft）· content_summary · is_deleted（软删除）
GuardianShareLink：log_id · token · expires_at · revoked · view_count · last_viewed_at（二期）

三通道：短信走既有 notification_service.send_sms()（只发提示+引导，A4）；报告走既有打印/导出方案；链接走 GuardianShareLink 只读页（7 天有效、可撤销、限流，A6）。

三挂接点（全手动触发）：① 请假提交时提示（A8，读 leave 状态决定文案）；② 危机干预新增"约谈家长"类型时同步生成台账（A9，扩展 crisis_service）；③ 学生档案页手动发起。

安全（A10）：手机号脱敏输出；危机类记录禁止生成分享链接；所有操作写审计。

验收：能建档联系人、能记录沟通、短信通道在未配置时优雅降级为 pending（不报错）；危机约谈能自动留痕；链接不可越权访问。

5P2 底座（立得住）

P2 不直接面向教师，但决定"数字教育"能不能真正成立。建议与 P0 同期启动、P2 阶段验收。

#模块核心设计关键约束
12 学情数据底座 LearningEvent（xAPI 精简版）：actor_id / verb / object_type / object_id / result_json / context_json / occurred_at；各业务模块通过 learning_event_service.emit() 单点写入 只提供写入与查询，不做业务判断；写入失败不得影响主流程（旁路、异常吞掉并记日志）

7风险与应对

风险影响应对
短信服务商未接入 家校沟通短信通道不可用 既有 notification_service 已预留降级：未配置时记 pending / not_configured，不报错，业务不阻塞；接入后零改动生效
匿名互评被"小样本反推" 匿名性被破坏，教师不敢填 结果页设最小样本阈值（如 < 5 份不出分布）；答卷表不存提交人；同一被评人限一次
任务表膨胀 / 重复推荐 首页待办噪音，教师不再信任 唯一约束 (source_type, source_id, teacher_id) + 过期自动归档 expired
P2 底座改造面过大 拖慢整体节奏，引发回归问题 审批引擎新旧并存、逐个迁移；学情底座旁路写入，失败不影响主流程
模块间隐性耦合 违背低耦合目标，后续难维护 跨模块只经 Service 公开函数；Code Review 检查是否存在跨模块 Model 直接 import
执行顺序建议：M1 的第 1、2 号模块先行（公共基座），同期启动 P2 的 12、14（只做骨架不验收）；M1 完成后立即并行推进 M2 的四个独立模块。
